# What Is an API?

**API** stands for Application Programming Interface. At its core, an API is a set of rules that allows one piece of software to talk to another.

Think of it like a restaurant menu: you (the client) don't need to know how the kitchen (the server) works internally. You just need to know what you can order (the available endpoints) and what format to use when ordering (the request format).

## The Client-Server Model

Every API interaction has two sides:

- **Client** — the one making the request (your browser, a mobile app, another server)
- **Server** — the one handling the request and sending back a response

The client and server are separate. They communicate over a network using a shared protocol — in the case of web APIs, that protocol is **HTTP**.

## What Makes It an "Interface"?

The word *interface* is key. An API is the public-facing layer of a system. Behind it, the server can be built in any language, store data in any database, and have any internal logic — as long as the interface (the set of endpoints and their expected inputs/outputs) stays consistent, clients don't need to know or care about any of that.

This is the same idea as a power outlet: you don't need to know how the power grid works to charge your phone. You just need the outlet to accept your plug.

## What You Just Received — JSON

The response you got back is **JSON** (JavaScript Object Notation). It's the universal format for API data because it maps directly to objects and arrays in almost every programming language.

JSON has exactly six value types:

```json
{
  "string": "hello",
  "number": 42,
  "boolean": true,
  "null": null,
  "array": [1, 2, 3],
  "object": { "nested": "value" }
}
```

In the response you saw:
- `data` — an array of user objects
- `total` — a number
- `_links` — a nested object with related URLs (this is a REST pattern called HATEOAS)

Every API you'll ever build returns JSON. Every API you'll ever call sends JSON back. It's the lingua franca of web APIs.

## The Anatomy of an HTTP Request

Every API call is made of two parts: a **request** and a **response**. Here's what each one looks like:

```
── REQUEST ──────────────────────────────────────
GET /api/playground/users HTTP/1.1
Host: localhost:3000
Accept: application/json

(no body — GET requests don't have one)

── RESPONSE ─────────────────────────────────────
HTTP/1.1 200 OK
Content-Type: application/json

{
  "data": [...],
  "total": 3
}
```

The request has:
- **Method** — what to do (`GET`, `POST`, `DELETE`, etc.)
- **URL** — which resource to act on
- **Headers** — metadata about the request (content type, auth tokens, etc.)
- **Body** — data being sent to the server (only for POST/PUT/PATCH)

The response has:
- **Status code** — did it work? (`200 OK`, `404 Not Found`, `500 Error`)
- **Headers** — metadata about the response
- **Body** — the data being returned (usually JSON)

## What Happens Under the Hood

1. Your browser sent an HTTP `GET` request to `/api/playground/users`
2. The server matched the URL to a route handler
3. The handler read from the data store and built a JSON response
4. The server sent back a `200 OK` with the JSON body

You just watched all four steps happen in real time.

## Why APIs Matter

APIs are everywhere:

- When you log in with Google, the site calls Google's API
- When you see a map embedded in a website, it's calling Google Maps' API
- When you get a weather update in an app, it's calling a weather service's API

Building your own API means any other system — a mobile app, a third-party service, another server — can interact with your data and logic in a structured way.
